# Contributing

Thanks for looking at this. The simulator exists so that people building the
cold chain data pipeline — country and employer system implementers, equipment
suppliers and integrators, researchers — can get realistic CCE monitoring data
without needing access to a real fleet. Contributions that make the generated
data *truer to the field* or *truer to the specification* are the most valuable
kind here.

## Where to file issues

**GitHub Issues is the front door:**
<https://github.com/phoenixgh-org/ems-data-simulator/issues>

That is where bugs, questions and feature requests belong. You do not need to
install anything to file one.

Internally the maintainers track work with [beads](https://github.com/steveyegge/beads)
(`bd`), and the issue database `.beads/issues.jsonl` is committed to this repo —
so you can read the real backlog, including design notes and dependencies,
without any special tooling. But **do not file there**: maintainers triage from
GitHub into beads, and an issue that only exists in a clone of `.beads/` will not
be seen.

### What makes a good report

Domain detail helps more than a stack trace usually does:

- A payload the CCE data delivery validator (`../cce-data-delivery-validator`)
  rejects — include the transmission and the validator's complaint.
- A data object whose bounds, units or precision disagree with the
  specification. Cite the spec: <https://docs.2to8.cc/cce-data-interop/overview/>.
  Annex 1 (Cold Chain Data Objects) is authoritative on bounds and units.
- A simulated fault signature that does not look like what you see in the field.
  Real traces (anonymised) are welcome and are the hardest thing to get.
- Anything where the Python and JavaScript implementations disagree.

Please include the config you used and the `random_seed`, so the run can be
reproduced.

## Development setup

Python 3.12 or newer; Node 22 is what CI runs.

```bash
git clone https://github.com/phoenixgh-org/ems-data-simulator.git
cd ems-data-simulator

pipenv sync --dev        # full dev environment (tests, notebooks, FHIR, Locust)
# or, for the runtime package only:  pip install -e .

cd js && npm install
```

If you change `Pipfile`, re-run `pipenv lock` in the same commit — CI runs
`pipenv verify` and fails on a stale lock. The pipenv version is pinned in
`.github/workflows/ci.yml`; bump the pin and re-lock together, never separately.

Runtime dependencies are declared once, in `pyproject.toml`. `Pipfile` installs
the project editable and adds dev-only tools.

## Running the tests

```bash
python3 -m pytest tests/ -q     # roughly 330 tests
cd js && npm test               # roughly 440 tests
```

Those counts are approximate and move with the code; treat a mismatch as normal,
not as a broken checkout. What matters is that both suites are green.

CI runs two further jobs on every pull request, and it is worth running them
locally if you touched `fhir/`:

```bash
python3 fhir/transform/run_phase2_poc.py   # FHIR R4 transform acceptance checks
cd fhir && npx fsh-sushi@3 .               # compiles the FSH profiles
```

## Conventions a newcomer will get wrong

These are the ones that actually cost people time. Please read them before
opening a pull request.

### 1. There are two implementations, and they must stay equivalent

`ccesim/` is the Python reference implementation. `js/` is a port. **If you
change the physics, the event model, the alarm rules or the emitted record
shape in one, the other has to follow in the same pull request.**

`js/src/cross-validation.test.js` is what enforces this. It runs the JS
simulator against reference fixtures generated by Python (in `js/fixtures/`) and
checks structural, physical, behavioural and format equivalence. It deliberately
does *not* compare values element by element: Python uses the Mersenne Twister
and the JS port uses seedrandom's ARC4, so identical seeds give different random
draws. Equivalence here means *same behaviour*, not *same numbers*.

### 2. Regenerating fixtures is a Python script

Run from the repo root:

```bash
python3 js/fixtures/generate_fixtures.py
```

It rewrites the eight scenario fixtures in `js/fixtures/` from the Python
simulator at a fixed seed. Regenerate them whenever a Python change legitimately
alters the reference output, commit the regenerated JSON alongside the change,
and say in the commit message why the fixtures moved. A fixture diff you cannot
explain is a bug, not a fixture problem.

(`js/fixtures/catalog/` is a small hand-maintained catalog used by the catalog
tests. It is not generated by that script.)

### 3. The naming split: snake_case, camelCase, and field names

This trips almost everyone:

| | Python | JavaScript |
|---|---|---|
| **API** (functions, methods) | `snake_case` — `default_config()`, `EventConfig.few_but_long()` | `camelCase` — `defaultConfig()`, `EventConfig.fewButLong()` |
| **Config and catalog field names** | `snake_case` | **`snake_case` too** — `random_seed`, `fault_type`, `Q_compressor`, `R`, `C`, `power_type` |

Field names stay identical across both implementations on purpose. Several are
physics notation rather than English words, and keeping them the same is what
lets a JS config be compared directly against a Python-generated fixture with no
translation layer. Do not "fix" a snake_case config field in the JS port — that
breaks cross-validation. Do follow camelCase for anything that is actually API
surface.

Data object identifiers (`TVC`, `TAMB`, `ALRM`, …) and catalog record fields
(`APQS`, `AMFR`, `AMOD`) come from the specification and are never renamed.

### 4. No issue IDs in source or documentation

Internal beads IDs (`ccesim-xxx`) were deliberately removed from all tracked
files: they are unresolvable for anyone outside the maintainers' tracker. Do not
add them to code, comments, README files or docstrings.

**Commit messages are the exception** — they carry the ID, which is how work is
traced back to the tracker.

### 5. Internal-only material goes in `docs/internal/`

That directory is gitignored. Anything not intended for the public repo —
working notes, deployment specifics, unpublished data — belongs there and
nowhere else.

### 6. Cross-repo references must be relative

Sibling projects are referenced relative to this repo's root — for example
`../cce-data-delivery-validator`, the companion validator this simulator feeds.
Absolute paths are machine-specific and dangle for everyone else.

## Pull requests

- Branch off `main`; keep the change focused on one thing.
- Both test suites green locally before you push. CI (`.github/workflows/ci.yml`)
  runs the Python suite, the JS suite, the FHIR transform acceptance checks and
  the SUSHI compile on every pull request, and all four must pass.
- Add tests. A physics or schema change without a test that would have caught the
  old behaviour is hard to accept.
- Commit messages: a terse imperative summary line, then a body explaining *why*
  — especially the reasoning and any scope boundary you held deliberately. Match
  what you see in `git log`.
- If a change alters emitted output, say what a consumer has to do about it. The
  simulator's payloads are the validator's working corpus, so output changes
  land on someone else's desk.
